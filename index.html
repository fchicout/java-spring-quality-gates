01

Restrições Arquiteturais & de Código

1.1Arquitetura em Camadas — Regras Rígidas

Fluxo de dependência obrigatório: Controller → Service → Repository → Domain, com DTOs cruzando apenas a fronteira do Controller.

#RegraJustificativa
R1Controller nunca injeta Repository diretamenteEvita acoplamento direto à persistência nos testes de camada web
R2Service nunca conhece tipos de jakarta.servlet ou anotações webRegra de negócio deve ser testável sem contexto HTTP
R3Repository não contém lógica de negócioRepository é infraestrutura, não domínio
R4Pacotes organizados por feature, não por camada técnica puraEvita a "camada Deus"; com.projeto.matricula.{controller,service,repository,dto}
R5Dependências fluem apenas para baixoNenhuma camada inferior conhece a superior — validado via ArchUnit

Enforcement automatizado obrigatório em test/, executado a cada build:

ArchitectureTest.java
@AnalyzeClasses(packages = "com.projeto")
class ArchitectureTest {

    @ArchTest
    static final ArchRule controllers_should_not_access_repositories =
        noClasses().that().resideInAPackage("..controller..")
            .should().dependOnClassesThat().resideInAPackage("..repository..");

    @ArchTest
    static final ArchRule entities_should_not_be_returned_by_controllers =
        noMethods().that().areDeclaredInClassesThat()
            .resideInAPackage("..controller..")
            .should().haveRawReturnType(resideInAPackage("..domain.."));

    @ArchTest
    static final ArchRule layered_architecture = layeredArchitecture()
        .consideringOnlyDependenciesInLayers()
        .layer("Controller").definedBy("..controller..")
        .layer("Service").definedBy("..service..")
        .layer("Repository").definedBy("..repository..")
        .layer("Domain").definedBy("..domain..")
        .whereLayer("Controller").mayNotBeAccessedByAnyLayer()
        .whereLayer("Service").mayOnlyBeAccessedByLayers("Controller")
        .whereLayer("Repository").mayOnlyBeAccessedByLayers("Service");
}

1.2DTOs e Mappers — Proibição de Vazamento de Entidade

Regra absoluta

Nenhum @Entity cruza a fronteira do Controller, em nenhuma direção — nem como parâmetro, nem como retorno.

AlunoRequestDTO.java
public record AlunoRequestDTO(
    @NotBlank(message = "Nome é obrigatório")
    @Size(max = 120)
    String nome,

    @NotBlank @Email
    String email,

    @NotNull @Past(message = "Data de nascimento deve ser passada")
    LocalDate dataNascimento
) {}

Mapper via MapStruct — proibido mapeamento manual campo-a-campo dentro do Service:

AlunoMapper.java
@Mapper(componentModel = "spring", unmappedTargetPolicy = ReportingPolicy.ERROR)
public interface AlunoMapper {
    Aluno toEntity(AlunoRequestDTO dto);
    AlunoResponseDTO toResponseDTO(Aluno entity);
    List<AlunoResponseDTO> toResponseDTOList(List<Aluno> entities);
}

unmappedTargetPolicy = ReportingPolicy.ERROR é obrigatório: força falha de compilação se um campo da entidade não tiver mapeamento explícito — evita vazamento silencioso de campo sensível (ex.: senhaHash) para o DTO de resposta.

1.3Tratamento Global de Exceções — RFC 7807

Uso obrigatório de ProblemDetail nativo do Spring 6 — proibido ResponseEntity<String> ou corpo de erro ad-hoc.

GlobalExceptionHandler.java
@RestControllerAdvice
public class GlobalExceptionHandler {

    @ExceptionHandler(RecursoNaoEncontradoException.class)
    public ProblemDetail handleNaoEncontrado(RecursoNaoEncontradoException ex) {
        ProblemDetail pd = ProblemDetail.forStatusAndDetail(HttpStatus.NOT_FOUND, ex.getMessage());
        pd.setTitle("Recurso não encontrado");
        pd.setProperty("timestamp", Instant.now());
        return pd;
    }

    @ExceptionHandler(Exception.class)
    public ProblemDetail handleGenerico(Exception ex, HttpServletRequest req) {
        log.error("Erro não tratado em {}", req.getRequestURI(), ex);
        // NUNCA expor ex.getMessage() de exceções não controladas ao cliente
        return ProblemDetail.forStatusAndDetail(
            HttpStatus.INTERNAL_SERVER_ERROR, "Erro interno inesperado");
    }
}
Auditado no Gate

O handler genérico nunca retorna ex.getMessage() ou stacktrace ao cliente — apenas loga internamente (OWASP A09, exposição de informação sensível em log/erro).

application.yml

Uso de @PreAuthorize — obrigatório na camada Service, nunca apenas no Controller (chamadas internas também precisam respeitar a regra):

}

1.5Persistência — Spring Data JPA + SQLite3

RestriçãoMotivo
hibernate.dialect = SQLiteDialect (community)Não incluso por padrão no Hibernate core
hikari.maximum-pool-size = 1SQLite serializa escritas a nível de arquivo — pool grande gera SQLITE_BUSY
PRAGMA journal_mode = WALPermite leitura concorrente durante escrita
Migração de schema exclusivamente via FlywaySQLite não tem ALTER TABLE robusto — ddl-auto: update corrompe silenciosamente

2.2Padrões de Teste

Unitário (Service) — JUnit 5 + Mockito, isolamento total, nomenclatura Given-When-Then:

MatriculaServiceTest.java
@ExtendWith(MockitoExtension.class)
class MatriculaServiceTest {

    @Mock private AlunoRepository alunoRepository;
    @InjectMocks private MatriculaService matriculaService;

    @Test
    @DisplayName("Deve efetuar matrícula quando aluno existe e não possui matrícula ativa")
    void deveEfetuarMatricula_quandoAlunoValido() {
        // Given
        var request = new MatriculaRequestDTO(1L, "2026.2");
        when(alunoRepository.findById(1L)).thenReturn(Optional.of(new Aluno()));

        // When
        var resultado = matriculaService.efetuarMatricula(request);

        // Then
        assertThat(resultado.status()).isEqualTo(StatusMatricula.ATIVA);
    }
}

Integração (Controller) — @WebMvcTest + MockMvc:

AlunoControllerTest.java
@Test
@WithMockUser(roles = "ALUNO")
@DisplayName("DELETE deve retornar 403 quando usuário não é ADMIN/SECRETARIA")
void deletar_deveRetornar403_semPermissao() throws Exception {
    mockMvc.perform(delete("/api/v1/alunos/{id}", 1L))
        .andExpect(status().isForbidden())
        .andExpect(jsonPath("$.title").value("Acesso negado"));
}
Regra

Todo endpoint deve ter teste cobrindo: (a) sucesso, (b) 4xx de validação, (c) 403 quando role incorreta — os três casos são exigidos no checklist de PR.

03

Fluxo de Git & Regras de Pull Request

3.1Proteção de Branch

main

  • PR obrigatório antes do merge
  • Checks: build, test, sonarqube-quality-gate
  • 1 aprovação mínima, descarta aprovações antigas
  • Sem force push, sem exclusão
  • Recebe merge apenas de release/*

develop

  • PR obrigatório antes do merge
  • Checks: build, test
  • 1 aprovação mínima
  • Sem force push

feature/* · fix/*

  • Sem proteção
  • Descartáveis após o merge

release/*

  • Criada a partir de develop
  • Só recebe correções de última hora
  • Merge em main e de volta em develop
.github/workflows/ci.yml
name: CI
on:
  pull_request:
    branches: [main, develop]

jobs:
  build-test-sonar:
    runs-on: self-hosted
    steps:
      - uses: actions/checkout@v4
        with: { fetch-depth: 0 }
      - uses: actions/setup-java@v4
        with: { java-version: '21', distribution: 'temurin', cache: maven }
      - run: mvn -B clean verify
      - name: SonarQube Quality Gate
        env:
          SONAR_TOKEN: ${{ secrets.SONAR_TOKEN }}
        run: mvn sonar:sonar -Dsonar.host.url=https://sonar.fchicout.dev -Dsonar.qualitygate.wait=true

3.2Checklist Obrigatório de Pull Request

.github/pull_request_template.md
## Checklist obrigatório
- [ ] CI (build-test-sonar) passou sem falhas
- [ ] SonarQube Quality Gate: verde
- [ ] Cobertura de testes do código novo ≥ 80%
- [ ] Nenhuma Entidade JPA exposta em Controller
- [ ] Testes unitários + integração para toda regra nova
- [ ] Commits seguem Conventional Commits
- [ ] Sem TODO/FIXME sem issue vinculada
Sem exceção

O PR só pode ser mergeado se todos os itens do checklist estiverem marcados, e o Quality Gate retornar OK, e houver ao menos 1 aprovação humana — nenhuma dessas três condições substitui a outra.

3.3Commits Convencionais & SemVer

TipoUsoEfeito em SemVer
feat:Nova funcionalidadeMINOR 1.2.0 → 1.3.0
fix:Correção de bugPATCH 1.2.0 → 1.2.1
refactor:Sem mudança de comportamento externo— nenhum release sozinho
test:Apenas testes— nenhum release sozinho
BREAKING CHANGE:Quebra de compatibilidade (rodapé)MAJOR 1.2.0 → 2.0.0
exemplos de commit
feat(matricula): adicionar validação de matrícula duplicada por período

fix(auth): corrigir mapeamento de grupo LDAP para ROLE_ADMIN

refactor(aluno): extrair AlunoValidator do AlunoService

Tag de release, criada apenas a partir de main:

shell
git tag -a v1.3.0 -m "Release 1.3.0: módulo de matrícula + integração LDAP"
git push origin v1.3.0

Configuração Multi-Profile

Estrutura: application.yml (comum) + application-{test,staging,prod}.yml.

ProfileBancoddl-autoObservabilidade
testjdbc:sqlite::memory:create-dropDEBUG completo
staging/data/staging/extensao.dbvalidateINFO + métricas
prod/data/prod/extensao.dbvalidateWARN, apenas health
application-prod.yml
spring:
  datasource:
    url: jdbc:sqlite:/data/prod/extensao.db
    hikari:
      maximum-pool-size: 1
  jpa:
    hibernate:
      ddl-auto: validate
  flyway:
    enabled: true
  ldap:
    urls: ${LDAP_PROD_URL}
    password: ${LDAP_ADMIN_PASSWORD}
logging:
  level:
    root: WARN
management:
  endpoint:
    health:
      show-details: never
Isolamento

Nenhuma credencial em application-{staging,prod}.yml — apenas ${VAR_AMBIENTE}. Ativação de profile nunca hardcoded no .yml: sempre via -Dspring.profiles.active=staging no deploy.
