01

Restrições Arquiteturais & de Código

1.1Arquitetura em Camadas & ArchUnit

Fluxo de dependência obrigatório: Controller → Service → Repository → Domain, com DTOs cruzando apenas a fronteira do Controller.

#Regra ArquiteturalJustificativa
R1Controller nunca injeta Repository diretamenteEvita acoplamento direto à persistência nos testes web
R2Service nunca conhece tipos de jakarta.servlet ou anotações webLógica de negócio deve ser testável sem contexto HTTP
R3Repository não contém lógica de negócioRepository é infraestrutura de persistência
R4Pacotes organizados por featureEvita a camada Deus; br.senac.fullstack.{feature}.*
R5Validação estrita em tempo de build com ArchUnitImpede regressões arquiteturais de dependências invertidas
ArchitectureRulesTest.java
@AnalyzeClasses(packages = "br.senac.fullstack", importOptions = ImportOption.DoNotIncludeTests.class)
public class ArchitectureRulesTest {

    @ArchTest
    static final ArchRule controllerClassesShouldBeAnnotatedWithRestController =
            classes().that().resideInAPackage("..controller..")
                    .should().beAnnotatedWith(RestController.class);

    @ArchTest
    static final ArchRule serviceClassesShouldBeAnnotatedWithService =
            classes().that().resideInAPackage("..service..")
                    .should().beAnnotatedWith(Service.class);

    @ArchTest
    static final ArchRule layeredArchitectureRule = layeredArchitecture()
            .consideringOnlyDependenciesInLayers()
            .layer("Controller").definedBy("..controller..")
            .layer("Service").definedBy("..service..")
            .whereLayer("Controller").mayNotBeAccessedByAnyLayer()
            .whereLayer("Service").mayOnlyBeAccessedByLayers("Controller");
}

1.2DTOs com Java 21 Records & Mappers

Regra absoluta

Nenhuma entidade JPA cruza a fronteira do Controller. Utilize Records imutáveis para DTOs com anotações de validação do Bean Validation.

HealthStatusDTO.java
public record HealthStatusDTO(
    @NotBlank String status,
    @NotBlank String application,
    @NotBlank String environment,
    @NotNull Instant timestamp,
    @PositiveOrZero long uptimeMillis
) {}

1.3Tratamento Global de Exceções — RFC 7807

Uso obrigatório do ProblemDetail nativo do Spring 6/3.x. É estritamente proibido retornar mensagens internas de erro não sanitizadas ou stacktraces ao cliente.

1.4Autenticação & Identidade — LLDAP SSO

O ecossistema utiliza autenticação centralizada no servidor LLDAP (https://lldap.fchicout.dev). Os estudantes autenticam utilizando seu usuário de e-mail (ex: christopher.carvalho) com permissões mapeadas via grupos LDAP (damatch_admin e azrael_admin).

1.5Frontend Moderno: Angular 22 Zoneless, Signals & OnPush

O frontend opera na vanguarda da arquitetura do Angular 22:

  • Zoneless (Sem zone.js): Inicialização e reatividade acionadas diretamente por Signals reativos (provideZonelessChangeDetection()).
  • Change Detection OnPush: Avaliação cirúrgica de componentes no DOM.
  • Control Flow Moderno: Diretivas legadas substituídas por @if, @else e @for nativos.

Quality Gates no SonarQube & Testes Automatizados

O servidor sonar.fchicout.dev adota o Quality Gate oficial e padrão "Sonar way" (baseado no princípio Clean as You Code). O pipeline do GitHub Actions valida e bloqueia o build (-Dsonar.qualitygate.wait=true) caso qualquer uma das seguintes regras seja violada no código novo:

Métrica (Chave Interna)OperadorCondição de ReprovaçãoLimite Obrigatório
Coverage on New Code (new_coverage)LT (Menor que)Menor que 80.0%≥ 80.0%
Duplicated Lines on New Code (new_duplicated_lines_density)GT (Maior que)Maior que 3.0%≤ 3.0%
Security Hotspots Reviewed (new_security_hotspots_reviewed)LT (Menor que)Menor que 100.0%100.0%
New Issues / Violations (new_violations)GT (Maior que)Maior que 00 Novas Violações
Clean as You Code

O Sonar way garante que todo novo commit ou Pull Request mantenha dívida técnica zero: zero novos bugs, zero novas vulnerabilidades, zero novos code smells, e no mínimo 80% de cobertura por testes automatizados.

2.2Padrões de Teste: JUnit 5, JaCoCo & Vitest

Backend: JaCoCo gera o relatório XML em backend/target/site/jacoco/jacoco.xml a cada execução de mvn test.

Frontend: O runner oficial Vitest 2.x executa os testes em milissegundos sem abrir navegadores pesados:

vite.config.mts
import { defineConfig } from 'vite';
import angular from '@analogjs/vite-plugin-angular';

export default defineConfig({
  plugins: [angular()],
  test: {
    globals: true,
    environment: 'jsdom',
    setupFiles: ['src/test-setup.ts'],
    include: ['src/**/*.spec.ts'],
    coverage: { provider: 'v8', reporter: ['text', 'lcov', 'html'] }
  }
});

DevSecOps: Pipeline de Segurança Contínua

A esteira de integração contínua implementa uma blindagem completa em 5 camadas (Shift-Left Security):

3.1Linting Obrigatório (Checkstyle & ESLint)

Verificação estática de código limpo e padrões arquiteturais executada antes de qualquer teste.

3.2SAST: Auditoria Estática com Semgrep

Analisa o código em busca de injeções de SQL/Comando, controle de acesso quebrado, má configuração de headers e antipadrões de segurança do Spring e TypeScript.

3.3Secret Scanning com Betterleaks

Utiliza o Betterleaks para varrer todo o histórico do Git e arquivos alterados, detectando tokens de API, senhas e certificados privados antes do merge.

3.4Supply Chain Security: Syft (SBOM) & Grype (CVEs)

O Syft gera o inventário de software padronizado (SBOM SPDX-JSON) e o Grype cruza as dependências contra vulnerabilidades conhecidas em tempo de compilação.

3.5DAST Diferenciado por Ambiente: Nuclei vs OWASP ZAP

  • Ambiente de Staging (Branch development): Varredura rápida orientada a templates com ProjectDiscovery Nuclei para feedback ágil aos desenvolvedores.
  • Ambiente de Produção (Branch main / Tags): Varredura profunda com OWASP ZAP Baseline Scan para homologação de releases.
04

Governança Git, Política de Branches & Happy Path

4.1Política de Branches

main (Produção)

  • 100% Protegida: Sem push direto
  • Recebe merges exclusivamente de development ao fechar uma versão
  • Dispara DAST (OWASP ZAP) e Deploy em Produção

development (Staging)

  • Branch base de integração do time
  • Entrada exclusiva via Pull Request aprovado
  • Dispara DAST (Nuclei) e Deploy em Staging

feature/* · bugfix/*

  • Ramificadas a partir da development
  • Uma branch por Issue (ex: feature/ISSUE-12-auth)
  • Descartáveis após o Squash & Merge

4.2O Caminho Feliz (Happy Path)

Ciclo de vida operacional padrão de um desenvolvedor desde o recebimento da Issue até a entrega em Staging:

sequenceDiagram
    autonumber
    actor Dev as 👩‍💻 Desenvolvedor
    participant Local as 💻 Git Local
    participant GitHub as 🐙 GitHub Remote
    participant Actions as ⚙️ GitHub Actions (CI)
    participant Staging as 🚀 Ambiente Staging

    Dev->>GitHub: 1. Pega uma Issue (ex: #12)
    Dev->>Local: 2. git checkout development && git pull origin development
    Dev->>Local: 3. git checkout -b feature/ISSUE-12-cadastro-usuario
    loop Ciclo TDD & Desenvolvimento
        Dev->>Local: 4. Implementa código e testes locais
        Dev->>Local: 5. mvn clean test & npm run lint test
    end
    Dev->>Local: 6. Commits Atômicos (Conventional Commits)
    Dev->>Local: 7. git fetch origin && git rebase origin/development
    Dev->>GitHub: 8. git push -u origin feature/ISSUE-12-cadastro-usuario
    Dev->>GitHub: 9. Abre Pull Request (feature -> development)
    GitHub->>Actions: 10. Executa CI (Lint, Tests, SAST, Betterleaks, Supply Chain, SonarQube)
    Dev->>GitHub: 11. Code Review & Aprovação dos colegas
    GitHub->>Local: 12. Squash & Merge no GitHub para 'development'
    GitHub->>Actions: 13. Dispara DAST (Nuclei) & Deploy Staging
    Actions->>Staging: 14. Aplicação atualizada em Staging!
